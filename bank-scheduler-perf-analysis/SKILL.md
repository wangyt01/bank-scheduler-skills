# 并发明细型调度任务性能分析

针对"多个工作线程逐条处理业务明细"型调度任务（收款自动入账、支付入账、批量回单等）的性能问题做归因分析。
核心方法：核实调度实参 → 重建工作线程会话 → 单笔耗时分布 → 日志间隔归因 → 无日志区间定位 → SQL 解码与失败原因 → 判定 → 报告。

适用形态与 `scheduler-perf-analysis`（报文往返型）互补：本技能面向无报文配对、靠 trace/线程聚合即可归因的场景。
开始前先加载 @references/gotchas.md。归因口径与统计陷阱都在其中，违反会得出错误结论。

## 输入

| 项 | 必需 | 缺省行为 |
|---|---|---|
| 日志根目录（`logging-YYYY-MM-DD.N.log` 分卷，gz/平铺/同名套目录均可） | 是 | 无则停止，请用户确认路径 |
| 工作线程关键词（如 `收款并发`） | 否 | 自动探测含 `thread` 的线程名，TOP 分布让用户确认 |
| 单笔开始标记（如 `自动入账开始[`） | 否 | 从组件日志候选中选，让用户确认 |
| 工程源码路径 | 否 | 用于核对日志打点位置、线程池、队列查询条件；线上版本可能与本地源码不一致，结论须标注"推断" |

日志格式为 GSP 标准行：`时间 主机 级别 [traceId] [模块] 类名 [线程名] 消息`。格式不符时脚本会提示解析率，此时停止并确认格式，不硬猜。

## 步骤

1. 环境检查：`python --version` ≥ 3.10（脚本仅用标准库）。缺 Python 时停止并告知，不猜测结果。
2. **核实调度实参（必做，最容易被忽略）**：
   `python scripts/sched_args.py --logdir <日志根目录>`
   重点核对三件事并写进报告：
   - 调度实参 JSON 里的 `threadCount`、`backDays` 等值——用户"说改了"不等于"真生效"（实例：参数写 4、用户以为是 7）；
   - 队列条数（"获取银行交易明细条数：N"）——用吞吐估算跑完一轮需要多久，和调度周期对比；
   - 调度进入/结束次数——判断是否存在上轮未结束又进下轮。
3. 会话重建与单笔耗时分布：
   `python scripts/analyze_slow.py --logdir <日志根目录> [--worker-keyword <关键词>] [--start-marker <单笔开始标记>]`
   输出：工作线程分布、单笔耗时 P50/P75/P90/P95/P99/MAX、分桶占比、最慢 TOP20、**步骤间隔归因 TOP35**（把每笔时间摊到具体日志环节）、单次最大间隔 TOP25。
4. 无日志区间定位（归因 TOP1 是"没有专属打点的区间"时必做）：
   `python scripts/trace_next.py --logdir <日志根目录> --anchor "<归因TOP1对应的日志片段>"`
   输出该锚点之后同一 trace 的下一行日志分布与间隔——锁定 0.3s 这类固定开销的归属区间；区间内线上代码无打点时，在报告标注"待部署分支确认"，不冒认定。
5. SQL 解码与失败原因：
   - base64 SQL 用 `base64 -d` 或 Python `base64.b64decode` 解码（日志中形如 `sql:xxx==`），重点看 OR + EXISTS、NOT IN 子查询、无索引等值列；
   - `python scripts/fail_reasons.py --logdir <日志根目录> --keyword <失败关键词>`
   输出失败原因 TOP：原因高度集中（如"未查到对应的组织往来单位"占比超九成）时，**无效明细治理**升级为 P0 候选。
6. 源码核查（提供了工程路径时）：grep 日志标记语句定位到类和行；核对线程池创建、队列查询是否带时间下限、失败明细是否更新状态退出队列；版本不一致时区分"已确认/推断"。
7. 判定（证据 → 结论，不许跳过证据直接下结论）：

   | 候选 | 判定证据 |
   |---|---|
   | 数据量大（积压） | 队列条数 × 单笔耗时 ≫ 调度周期；明细 transactionDate 最早日期距今天数 |
   | SQL 慢 | 解码后 SQL 有 OR/EXISTS/NOT IN 且该环节间隔均值显著高于其他查询 |
   | 单笔固定开销高 | 间隔归因 TOP 集中在某个环节（尤其未打点区间），单笔均值高但每笔 SQL 都不慢 |
   | 无效功放大 | 失败原因集中 + 失败明细不退出队列 + 每轮全量重扫 |

8. 报告（Markdown，结论先行）：
   - 一段话结论：直接回答"是数据量大、SQL 慢、还是其他"，用数字支撑；
   - 总体运行表（线程数/笔数/吞吐/单笔分位数/成功率）、归因表（总耗时/占比/次数/均值/最大）、SQL 快慢分列、代码发现（带类名行号）、行动建议 P0-P2（每条写预期收益）；
   - 若是调整后复查，加"调整前 vs 后"对比表，并明确指出"哪个调整没生效、哪个调整无效"；
   - 附可复跑的脚本命令。

## 质量自查

- [ ] 调度实参已从日志核实，未采信用户口述
- [ ] 归因表每行有 总耗时/占比/次数/均值/最大 五个数字
- [ ] 最大开销环节做过下一行定位，未打点区间已标注"推断"
- [ ] 失败原因 TOP1 占比已计算，失败明细是否退出队列已核实
- [ ] 吞吐 = 笔数 ÷ 墙钟时间（不是 笔数 ÷ 单笔均值 × 线程数）
- [ ] 结论四候选逐一给出证据或排除理由

## 停止条件

- 日志解析率 < 80%：格式不符，停止并让用户确认格式。
- 日志目录为空或无工作线程命中：确认是否拿错环境/节点。
- 未做间隔归因就下"SQL 慢"或"数据量大"结论：退回重做。

## 脚本失败状态

所有脚本只读日志，失败时以非零码退出并打印原因：目录不存在（确认路径）、无 gz/（确认解压）、解析率过低（确认格式）。重跑命令即重试，无状态残留。
