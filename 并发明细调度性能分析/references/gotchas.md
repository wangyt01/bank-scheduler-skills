# 日志归因陷阱（Gotchas）

违反本页任何一条都可能得出错误结论。分析前通读，报告前对照自查。

## 1. 口说无凭：调度实参必须从日志核实
用户说"线程改成 7 了"，日志实参可能是 `"threadCount":4`（真实案例：116 环境）。所有参数类结论（线程数、回溯天数、单位过滤开关）以 `多线程进入构件[...]` 行打印的 JSON 为准。配置改动不生效、改错环境、改错字段是高发错误。

## 2. 间隔归因口径
- 间隔 = 同一 traceId 内相邻两行日志的时间差，**归属前一行**：它度量的是"这行日志打印完 → 下一行日志打印前"发生的所有事（含无打点的查询、RPC、锁等待）。
- 必须先按 traceId 分组再排序，直接按时间排序会把多线程的行穿插串成假序列。
- 单次间隔超过阈值（默认 120s）视为跨批次/空窗，丢弃，否则归因表被一个悬挂间隔污染。
- 吞吐 = 处理笔数 ÷ 墙钟时间。用"单笔均值 × 线程数"推算吞吐会高估（线程有空闲）。

## 3. 线上版本 ≠ 本地源码
归因 TOP 落在一个本地源码里只有几行内存操作的区间（如 0.3s 固定开销），大概率是部署分支与本地源码有差异。处理方式：定位到"区间"并写报告标注"待部署分支确认"，加计时日志核实；**不要**凭本地源码断言"这里不可能慢"。

## 4. 业务流水是 ERROR 级
GSP 财司组件惯用 `log.error` 打业务流水，不能按日志级别过滤"错误"；按组件类名 + 线程名关键词过滤。

## 5. 分卷双份，防重复计数
目录里常有 `xxx.5100.log`（目录，内含同名平文件）与 `xxx.5100.log.gz` 并存，内容相同。脚本只取 gz、跳过同名平文件；手工分析时选一种，否则行数翻倍、占比失真。

## 6. 失败明细可能不退出队列（自我放大）
失败原因高度集中（如"未查到对应的组织往来单位"占 98.6%）时，必须核查失败后明细状态是否更新：不更新则每轮调度重复全量失败，队列永远追不平。这是"调整任何参数都没用"的常见根因。
失败明细若经 RPC 登记类机制（如写生单失败记录）落库，队列 SQL 在本地源码里往往看不出排除条件——"是否退出队列"的可靠验证是**下一轮日志的队列条数是否下降**，报告应将此列为复查项。对账口径：队列条数 = 进入单笔处理的明细数 + 抛异常被拦截的明细数（真实案例：534 = 77 + 457，精确吻合，可反向验证线程日志口径无遗漏）。

## 7. 队列规模对时间过滤不敏感
历史积压明细的 transactionDate 大多集中在最近几天，把回溯 24 天改成 7 天几乎不减少队列条数（真实案例：仍有 35,879 条）。判断"数据量大"看队列条数 × 单笔耗时与调度周期的关系，不看回溯天数改没改。

## 8. base64 SQL 要解码再评价
日志里 SQL 以 base64 出现。不解码就下"SQL 慢"结论不可靠：真实案例中看起来最重的查重 SQL 实测 21ms，反而"按名称查往来单位"的 OR + EXISTS 才是 0.96s。先解码、再看该环节的实际间隔均值。

## 9. 冷启动长尾
批次最初几笔 6~9s（连接池/缓存冷启动）属正常，不要拿 MAX 说是瓶颈；看 P95/P99 与归因表总量。

## 10. 对比分析的可比性
不同环境（87 vs 116）单笔耗时、吞吐可比；队列条数、失败占比受当地数据影响，只能作参考。对比表里要写明两窗口的时间范围与线程数，否则结论不成立。

## 11. 共库多任务污染：先圈组件口径，再做线程聚合
生产日志卷常由同节点几十个调度任务共写，且共用平台统一调度线程池（形如 `*_JOB_SCHEDULER_Worker-N`）。按线程关键词直接聚合归因，TOP 会被资金池/票据/预警等其他任务淹没（真实案例：归因 TOP1 是别的任务"没有获取到预警数据"，41981s，与目标组件无关）。正确顺序：先按组件 logger 类名或业务标记（如"收款自动入账"）过滤出本组件行（`analyze_slow.py --scope`），再在口径内看线程分布与间隔归因。

## 12. 工作线程只占总耗时零头时，调参数必然无效
先用「进入构件 → 获取条数 → 构件结束」三个锚点切分墙钟（配对统计可用 `analyze_slow.py --pair`）。若工作线程活跃时长（首末日志差）占墙钟 <5%，瓶颈在进入构件之后、起线程之前的同步前置逻辑（真实案例：智能认领规则过滤按 单位×规则 串行查询，202 单位 × 2 规则，单次 P50=18.19s，合计占墙钟 97.7%；工作线程只活跃最后 43s）。此时调 threadCount/backDays 无效，报告须写明"明确无效的调整"及数字依据。

## 13. 解码 SQL 后检查括号与 OR 优先级
规则/配置生成的过滤 SQL 常见缺陷：`AND (A) OR (B) AND unit=...` 缺一层括号，因 AND 优先级高于 OR，第一分支脱离单位/状态过滤 → 全表扫描。两个旁证可远程确认，不依赖 EXPLAIN：
a) 不同参数（不同单位）执行返回几乎相同的行数（真实案例：202 个单位全返回 ~315 行）；
b) 耗时方差极小（P50≈P90，真实案例 18.19s vs 18.61s）= 确定性全表扫描，非网络抖动。
对照组：同库另一规则的 OR 组被完整括号包裹且各分支带单位过滤，单次仅 0.15s。
