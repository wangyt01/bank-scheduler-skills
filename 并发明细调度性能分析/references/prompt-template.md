# 提示词模板：下次遇到"调度任务慢"怎么问

把方括号内容替换成实际值。要素齐了，第一轮就能出归因表；缺了也能跑，报告会把缺项标为"未提供"。

## 模板一：标准分析（最常用）

```text
分析调度任务【任务名】为什么慢。
日志目录：D:\补丁\日志1\...\xxlog（logging-YYYY-MM-DD.N.log 分卷，gz 已包含）
工程源码：D:\projects\gitlab\cashmanagement\...\组件.java（可选）
关注：是数据量大、SQL 慢，还是单笔固定开销高/无效明细拖累？
产出 Markdown 分析报告：结论先行、归因表、SQL 解码、失败原因 TOP、
调度实参核查（线程数/回溯天数是否真生效）、P0-P2 优化建议。
```

## 模板二：参数调整后复查（"改了反而更慢"）

```text
我们把【线程数/回溯天数/开关】从【旧值】调整成【新值】了，反馈变得更慢。
新日志：D:\补丁\...\新环境log
旧日志：D:\补丁\...\旧环境log（上次分析过，报告在 xxx.md）
请：1) 从日志实参核实新参数是否真生效；2) 新旧两份日志做单笔耗时/吞吐/归因对比；
3) 明确指出哪个调整没生效、哪个调整无效、真正变慢的原因。
```

## 模板三：只查一个疑点（快速验证）

```text
在日志 D:\...\xxlog 里核实两件事：
1) 调度实参 JSON 里 threadCount/backDays 到底是多少（以日志为准，别信配置描述）；
2) "获取银行交易明细条数"是多少，按最近一次吞吐估算跑完一轮要多久。
```

## 模板四：失败明细治理

```text
日志 D:\...\xxlog 中该调度 9 成以上明细失败（原因：未查到往来单位）。
请统计失败原因 TOP 及对应账号/单位清单（可导出），核查失败明细的状态是否更新、
会不会下轮重新入队，并给出"修主数据 + 代码短路"的治理方案。
```

## 让分析更快更准的三个习惯

1. **日志目录给到最内层**（含 .gz 的那层），别给到日期上层目录。
2. **附上工程源码路径**，且说明部署分支号——归因到"未打点区间"时能快速对照。
3. **先说结论再要报告**：如果你只想验证某个怀疑（如"是不是 SQL 慢"），用模板三，几分钟出结果；要完整报告用模板一。
