# 事故复盘：2026-09-28 三次 SSH/远程失联（一天内连环）

本文件是 `lighthouse-ssh-guard` 技能的事实依据。三条铁律 + 僵死识别签名均从这三次事故提炼。

## 事故 1：22 端口"时好时坏"

### 时间线
- 用户报"服务器无法连接"。
- 初步排查：实例 RUNNING、负载正常、全部服务在监听、云防火墙规则完好、root 密码未被改、无 fail2ban/hosts.deny 封禁——服务端一切正常。
- 本机实测出现矛盾证据：ping 通、3001/80/8888 HTTP 正常，但 22 端口 TCP 能连、SSH banner 收不到（6 秒超时）；且不同时段时好时坏。
- **误判**：据此怀疑"公司网络对 22 端口深包拦截"（历史上公司确实封过 GitHub SSH:22，症状也吻合）。
- 深挖服务端 secure 日志后真相大白：**互联网爆破 5.3 万次失败**，sshd 默认 `MaxStartups 10:30:100`——未认证并发超 10 个后按概率随机丢弃新连接。日志特征：`banner exchange: invalid format`、大量 `preauth` 断开。

### 修复
```
MaxStartups 100:30:300
LoginGraceTime 30
LogLevel VERBOSE
```
`sshd -t` 校验 → `systemctl reload sshd`（不断现有连接）→ 生效。

### 教训
1. 症状"时好时坏 + TCP 通但无 banner"在公网服务器上**首先怀疑 MaxStartups**，而不是网络设备；
2. `sshd -T` 查看生效配置时顺手核对 `maxstartups`；
3. 公网 22 端口的爆破量级要定期量化（`grep -c 'Failed password' /var/log/secure*`），涨到十万级就该上 fail2ban。

## 事故 2：追加 443 备用通道，22 被顶掉（更严重）

### 时间线
- 为绕开（当时误判的）公司网络对 22 的干扰，决定给 sshd 加 443 备用监听。
- 执行了**看起来完全正确**的操作：往 `sshd_config` 追加 `Port 443` → `sshd -t` 语法通过 → `systemctl reload sshd` 成功 → 云防火墙 443 本就放行。
- 之后从外部测试：443 间歇超时、22 也连不上——症状进一步强化了"公司网络干扰"的误判，甚至一度怀疑整条线路间歇丢包。
- 直到**下一会话**从服务端执行 `ss -tln` 才发现真相：**监听列表里只有 `:443`，没有 `:22`**。

### 根因
原 `sshd_config` 中 **22 端口仅靠默认值隐式生效**（文件内只有注释 `#Port 22`）。sshd 的规则：**一旦出现任何显式 `Port` 指令，"默认 22"立即失效**。追加 `Port 443` 后 sshd 只监听 443。`sshd -t` 不报错、reload 成功——没有任何信号提示 22 消失了。

### 修复
```bash
# 配置中 Port 区块修正为两行并存
Port 22
Port 443

sshd -t && systemctl reload sshd
ss -tln | grep -E ':(22|443)\b'     # 双端口都在监听
# 外部客户端实测双端口 banner，均 0.4s 内返回 SSH-2.0-OpenSSH_9.3
```

### 教训
1. **显式即排他**：显式写任何一个 `Port`，就必须显式写全所有需要的端口；
2. `sshd -t` 合法 ≠ 22 还在监听，**变更后必须 `ss -tln` 核对**；
3. "连不上"的第一反应应该是服务端 `ss -tln`，而不是网络侧猜测——本事故若第一时间执行该命令，30 秒可定位，却绕了一大圈"网络干扰"的弯路；
4. AI 远程会话切换（上一会话改配置、下一会话才发现断连）意味着**变更和验证必须在同一会话内闭环完成**。

## 对"初步误判"的反思

两次事故中，"公司网络干扰 22"这个假设两次被拿出来解释症状，两次都是错的（至少不是主因）。教训：**服务端可观测证据（日志、监听列表）的优先级永远高于客户端网络现象的推测**。先取证、后归因、再动手。

## 遗留风险
- 443 备用通道保留（防火墙已放行、nginx 未占用 443），22+443 双监听并存；
- 爆破防护目前靠 MaxStartups 调优 + VERBOSE 日志观察，fail2ban 暂未部署；
- `sshd_config.bak_20260928` 备份保留在 `/etc/ssh/`。

## 事故 3：guest 系统级僵死（22/443 TCP 通但零 banner，TAT/监控全灭）

### 时间线（14:40 前后发现）
- 上午修复事故 1/2 后，SSH 22+443 双监听、banner 0.4s 正常，远程任务（CodeBuddy）继续执行交接任务。
- 下午用户再报"连接不上"。取证：
  - 客户端：22/443 TCP 三次握手 0.2s 成功，但 **6 次抓取 banner 全部超时**——TCP 层由内核完成，应用层 sshd 无法响应；
  - 80/3001/8888/9000 等 Web 服务正常——改动前已启动的常驻进程幸存；
  - TAT：先 `DELIVER_FAILED`×2，随后 API 报 **"当前未安装 TAT"**——tat_agent 进程消失/僵死；
  - 云监控 `get_monitor_data` 全指标无数据——监控代理同样停摆；
  - 控制台防火墙规则完好（22/443 均 ACCEPT）——排除防火墙与网络层。

### 诊断推理
"内核能完成握手 + 应用层全灭 + 常驻进程幸存 + 云厂商 agent 全灭" = **guest 系统资源/进程空间僵死**（fork 耗尽或进程表损坏）。此时查 sshd_config、防火墙都是浪费时间。

### 恢复
- 远程 API（TAT）已死，AI 无法自救；WebShell 若可登录则先取证再清理，否则**控制台重启实例**是唯一有效手段。
- 重启安全性前提：cron 任务幂等（aipub 三条按日期落盘）、docker 容器 `--restart always`、关键服务 systemd enabled。

### 教训
1. **AI 无权触碰腾讯云 agent 组件**（tat_agent/stargate/barad/sgagent）——它们是远程运维最后的生命线，杀了它们 = AI 自废武功 + 用户失联；
2. 僵死签名要背下来：**TCP 通无 banner + TAT 未安装 + 监控无数据 + Web 活着**，四条同时成立立即走控制台重启，不要再折腾 SSH 层；
3. TAT 失败有两种语义要区分：`DELIVER_FAILED`（agent 在但异常）vs **"当前未安装 TAT"**（agent 心跳丢失已久）——后者说明 guest 已僵死较久；
4. 远程自动化（AI）对生产服务器执行任务前，应确认系统有资源余量（内存/进程数），并在任务后验证 agent 存活（`systemctl is-active tat_agent`）。
