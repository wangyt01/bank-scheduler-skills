# 财司历史明细获取性能分析

针对银企直联「财司历史明细获取」（调度任务 HisDetails）的性能问题做归因分析。
核心方法：全量扫描调度日志 → 提取事件时间线 → REQ/RESP 逐页配对 → 分段耗时归因 → 三候选判定 → HTML 报告。

开始前先加载 @references/gotchas.md。日志布局与统计陷阱都在其中，违反会得出错误结论。

## 输入（缺失时先向用户要齐）

1. 日志根目录：包含 `logging-YYYY-MM-DD.N.log` 分卷（目录套同名文件，或平铺文件）。
2. 每次执行的起止时间与条数表现，例如：第一次执行 2026-09-01 00:03:51 ~ 03:50:49，14728 条历史。
3. 业务日志标记（可选）：默认 `HisDetails 历史明细查询`；不同环境可能不同，可先 grep 确认。

## 步骤

1. 环境检查：`python --version` ≥ 3.10 即可（脚本仅用标准库）。缺 Python 时停止并告知用户，不猜测结果。
2. 建分卷时间索引（只读）：
   `python scripts/build_index.py --logdir <日志根目录> --out log_index.json`
3. 全量事件扫描（只读，几 GB 日志约数分钟）：
   `python scripts/scan_events.py --logdir <日志根目录> --tag "HisDetails 历史明细查询" --out events.csv`
   事件类型：REQ 待发送报文 / RESP 返回报文 / SKIP 已存在,跳过 / INSERT insert count / REC 交易记录 / BACKFILL 触发回查 / DATEUPD、DATEUPD_SKIP 查询日期推进。
4. 返回条数统计（处理被真实换行拆开的大报文）：
   `python scripts/count_bills.py --logdir <日志根目录> --tag "HisDetails 历史明细查询" --run "RUN1=<起>|<止>" --run "RUN2=<起>|<止>"`
5. 分段归因与对账：
   `python scripts/analyze_run.py --events events.csv --run "RUN1=<起>|<止>" --run "RUN2=<起>|<止>"`
6. 三候选判定（每一项都必须给出证据后才能下结论）：

   | 候选 | 判定为是的证据 |
   |---|---|
   | 单条入库慢 | 本地处理（RESP→下一事件）中位达数百 ms 以上，或入库环节耗时占比显著 |
   | 慢SQL | 日志出现慢查询记录，或结合执行计划另行分析 |
   | 报文往返慢 | RTT 合计占墙钟 > 80%，且本地处理中位为毫秒级（同时排除前两者） |

7. 根因链核查清单（逐项核对）：
   - 并行度：事件线程是否只有 `TaskThread-0`（单线程）；日志中 `配置的线程数` 的值。
   - 空页占比：BillNum=0 的页占比（count_bills 输出）。
   - 查询日期水位：DATEUPD_SKIP 多且第二轮请求几乎全为第 1 页 → 日期不前进导致重复全量查询。
   - 账户×日期组合数：组合数 × RTT ≈ 总耗时，验证构成。
   - RTT 方差：中位≈P90 且方差极小 → 疑似服务端固定延迟，不是网络抖动。
8. 对账：入库条数（INSERT 行的 **count 值求和**，不是行数。注意写同一张明细表的渠道不止一个——`Details 当日明细查询` 的 transType 也标 HisDetails，按 id/transType 圈定范围并在报告中写明口径）+ SKIP 条数 vs 银行返回条数（BillNum 合计）vs 用户给的条数表现；偏差 > 10% 时必须找出原因并在报告中标注，不得强行下结论。
9. 生成 HTML 分析报告，固定章节：一句话结论 → 关键数据表（墙钟/请求数/RTT 占比/空页占比/入库条数）→ 三候选判定表 → 根因链 → 分级优化建议 → 数据质量说明（截断/乱码/对账偏差）。
10. 优化建议分级基线：
    - P0：调度配置表中 HisDetails（对应 bankno）行的并发线程数调 3~5（账户级并发，不改代码）；查询日期按账户推进/记录水位，砍掉重复空查询。
    - P1：与银行/财司核查 RTT 固定延迟；若支持 StartDate~EndDate 区间查询，把多日合并为一次请求。
    - P2：附带发现的大报文日志刷屏治理（单卷可达百 MB 级）。

## 质量自查

- 每个数字都有日志证据来源（事件计数、配对数、BillNum 合计）。
- RTT 合计 + 本地处理 + 间隙 ≈ 墙钟（偏差 < 10%），对不上先查漏再下结论。
- 三候选每个都明确"排除/确认"，不给无证据归因。
- 报告区分"已实测数字"与"推断"。

## 停止条件

- 日志目录不存在或没有分卷 → 停止，请用户确认路径与解压方式。
- 扫描后目标事件数为 0 → tag 不匹配，先 grep 实际业务标记再重扫，不得空跑出报告。
- 对账偏差 > 10% 且找不到原因 → 报告标注"未对齐"，把已知与未知分开陈述。
